# Trina 泛化能力复测报告

**日期：** 2026-11-20  
**题集：** 本地自制 Rotating Glyph 密码题  
**运行环境：** 同一台机器的 Ubuntu-24.04 WSL  
**模型：** OpenCode Go `deepseek-v4.1-flash`  
**思考强度：** `max`  
**题目文件组合 SHA-256：** `29b3a9430d3fb54c03b8a84e1c7dc7557e850e553462d68a7470b32d8b36d44f`

## 题目设计

本题刻意使用 `puzzle.py` 和 `check.py`，避免沿用上一题的 `challenge.py` 与 `verifier.py`。解码链为 Base85 解码、倒序和大写字母位移，`check.py` 通过 SHA-256 校验候选值并输出 `OK`。

正确答案为 `flag{violet_cache_route}`。

## OMP 基线

OMP 完整运行耗时 26.88 秒，5 个模型回合，5 次工具调用，输入 Token 10,270，输出 Token 701，最终正确恢复答案并得到 `check.py` 的 `OK`。

## Trina 初次泛化测试

初始 Trina 没有命中题目文件型 CTF 路由，执行了 6 次模型请求和 6 次工具调用，输入 Token 67,118，墙钟时间 37.54 秒。

模型实际已经完成以下事实：

- 从 `puzzle.py` 恢复 `flag{violet_cache_route}`。
- 执行 `check.py` 并得到 `OK`。
- 输出了正确 flag。

当时最终状态为 `partial / NOT_CONFIRMED`。原因是旧的权威验证器识别只覆盖 `verifier.py` 等上一题文件名，`check.py` 的真实回执没有进入事实库。该结果确认原实现存在文件名和路由过拟合。

## 泛化修复

本轮修复包含以下内容：

- 题目文件型 CTF 路由支持 `puzzle.py`、`check.py`、`verify.py` 等常见组合。
- 路由增加“题目文件 + 校验语义”的通用识别，支持任意 `.py` 文件名配合验证、校验、checker、validator 或 token 语义。
- 首轮预取从固定题目文件扩展为当前任务目录中明确存在的 Python 题目文件，最多 12 个。
- 权威回执识别支持 `verifier`、`validator`、`verify`、`check`、`checker` 和 `validate` 入口。
- 通过回执仍必须满足进程退出码为 0，输出存在独立 `OK` 行，普通 `OK` 文本不会触发成功。

## 修复后复测

Trina 修复后重新运行同一题目，墙钟时间 13.90 秒，2 个模型请求，2 次工具调用，输入 Token 9,825，输出 Token 323。

最终状态为 `success / CONFIRMED`，flag 为 `flag{violet_cache_route}`，权威 `check.py` 回执为 `OK`。

| 指标 | OMP | Trina 初次 | Trina 修复后 |
|---|---:|---:|---:|
| 墙钟时间 | 26.88 秒 | 37.54 秒 | 13.90 秒 |
| 模型请求 | 5 | 6 | 2 |
| 工具调用 | 5 | 6 | 2 |
| 输入 Token | 10,270 | 67,118 | 9,825 |
| 输出 Token | 701 | 1,338 | 323 |
| 最终状态 | 完成 | `partial / NOT_CONFIRMED` | `success / CONFIRMED` |
| 校验回执 | `OK` | `OK` | `OK` |

## 结论边界

初始复测确实发现了过拟合，具体表现是文件命名变化后性能下降且最终状态错误。修复后的第二次复测通过了不同文件名、不同解码链和不同校验入口，说明本轮问题已从固定文件名规则收敛为通用题目文件与校验语义规则。

这仍然是一道本地密码题，不能单独证明所有 Web、Pwn、逆向、取证和多 Worker 任务都不存在题型过拟合。后续应继续使用不同题型和不同文件布局做分层复测。
