# OMP 与 Trina 双文件代码修复对比

日期：2026-11-21
题目：全新本地 Python 双文件修复任务
环境：同一台机器、同一 Ubuntu 24.04 WSL，同时启动
模型：OpenCode Go `deepseek-v4.1-flash`，思考强度 `max`
权威判定：`python3 -m unittest -v` 的 4 条测试全部通过

## 题目与基线

题目包含两个互不依赖的缺陷。

- `normalize_headers` 没有清理名称、忽略空名称或按原顺序合并重复值。
- `retry_delays` 对每次重试都返回相同延迟，没有按索引指数增长。

初始测试为 1/4 通过、3/4 失败。两套 Agent 使用独立的相同副本，收到同一英文任务说明。

## 真实结果

| Agent | 墙钟 | 最终测试 | 结果 |
| --- | ---: | ---: | --- |
| OMP 19.0.1 | 18.92 秒 | 4/4 | 通过 |
| Trina 0.5.0 | 19.08 秒 | 4/4 | `success / CONFIRMED` |

两者墙钟相差 0.16 秒，在本次单轮样本中可视为同级。OMP 快约 0.8%，这个差异不足以支持稳定排名。

Trina 首轮批量读取题面、两个实现文件和测试，实际运行失败基线，然后一次 `workspace_edit_many` 提交两个文件修改，最后用 `terminal_exec` 得到 4/4 通过的权威回执。运行记录为 3 次模型请求，输入 20,099 Token、输出 495 Token。OMP 文本模式没有暴露可核对的模型请求和 Token 明细。

两个 Agent 最终实现的行为一致，均保留公开函数签名，并通过同一测试文件重新验证。

## 结论边界

本题验证了 Trina 的代码任务路由、首轮预取、失败基线、多文件原子编辑和测试确认闭环。结果支持“在这道新的双文件 Python 修复题上，Trina 与 OMP 完成质量和墙钟处于同级”。单题、单轮结果不能证明所有编程任务全面追平，后续仍需覆盖大型仓库、编译型项目、失败恢复和长时间后台任务。
