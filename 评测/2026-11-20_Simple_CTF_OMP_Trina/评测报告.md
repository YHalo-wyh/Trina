Trina 最终状态显示为 `partial / INCONCLUSIVE`，原因是本地题目没有注册 `flag` 目标，`prove_goal` 返回目标不存在。题目自带 `verifier.py` 已真实执行并输出 `OK`，因此该状态属于终态判定适配缺口，不能否定实际解题结果。

## 修复后回归

本轮补上了 `terminal_exec → RunState.absorb → casebook → prove_goal → 最终 verdict` 的权威验证器事实链。只有命令参数明确指向 `verifier`、`verify`、`check_flag` 或 `validate_flag` 入口，进程退出码为 0，且输出存在独立 `OK` 行时，才登记通过回执并提取同一命令中的 flag 候选。普通命令输出 `OK` 不会触发该路径。

使用 Replay 复现“执行验证器并输出 `OK`”的最小回归后，实际状态为 `success / CONFIRMED`，`flags=1`，验证证据仍保留在原始命令工件中。该回归验证的是终态适配链，不能替代再次调用 OpenCode Go 的真实模型性能测试。

## 质量结论

- 两个 Agent 都恢复了相同 flag，并完成了独立验证。
- OMP 在本题的墙钟时间约为 Trina 的 16.1%，工具调用更少。
- Trina 的 Binary 路由和事件流优化没有影响标准工具执行和验证器结果。
- Trina 的本地任务收尾需要识别题目目录中的权威验证器，避免验证器已通过时仍显示 `INCONCLUSIVE`。
