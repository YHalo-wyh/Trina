# Intent：受控安全测试与仓库交付

## INT-01 产品意图

**提出背景。** 授权靶场测试包含端口和服务识别、路径发现、漏洞验证、取证和报告。手工串接工具容易丢失上下文，直接让模型操作 Shell 又难以统一判断目标、动作等级和证据质量。Trina 的产品目标是把这些步骤组织成一条可追踪的执行流程，操作者给出目标和任务后，可以检查每一步为什么执行、实际观察到什么、还有哪些检查未完成。

**预期结果。** 对能够连接的课程靶机，系统产生实际工具结果、结构化状态、可校验审计及可读报告。对不满足范围、预算或证据条件的任务，系统记录拒绝、失败和未覆盖部分。模型的成功声明不能写入已验证事实。操作者保留审批、提示、停止和撤权能力，复核者能够从报告反向定位证据。

**影响对象。** 操作者承担目标配置和批准责任；实现维护者维护工具契约和拒绝规则；模型负责提出候选动作；确定性执行链负责裁决并吸收事实；教师或结对复核者检查证据与结论。项目没有多人账号后台，以上是工程责任角色，不能当作已实现的登录和 RBAC 功能。

**来源与状态。** 来源为项目现有 README、`brief/README.md` 和课程项目代码，基线为 `24fb637`。状态为“既有产品意图，按代码基线归档”。此状态表示当前工作沿用已有项目范围，不代表教师已经接受全部功能、性能或研究主张。规格中的可观察行为、实现缺口和验收方式分别另行记录。

## INT-02 本次文档与提交意图

**原始请求。** 仓库维护者要求参照章节 02 课件的提交要求，把需求、规格和说明文档写具体，并上传到用于教师检查的 Gitee 仓库。交付位置是现有 `YHalo/Trina`，检查对象为仓库中的版本化内容。

**预期结果。** 教师无需依赖聊天记录即可找到问题框架、规格、状态模型、影响分析、方案决策、计划任务、双层 Harness、AI 使用披露和未决问题。抽查任一强制要求时，应能找到场景、可观察结果、实际验证入口及证据范围。文档中的命令和路径可以在当前仓库使用，历史样本与当前验证结果有独立版本说明。

**接受门。** 状态为 `Accepted for documentation and repository delivery`，依据是维护者本次明确的文档补齐和推送请求。允许工作包括阅读给定课件与现有代码、编写仓库文档、运行已有测试及回环机制验证、增加文档追踪检查、提交并推送。该接受门没有批准扩大产品攻击范围，也没有批准引入收费模型实验、重写安全控制器或代签课程审查。

**接受责任。** 仓库维护者确认交付目的与提交位置；文档维护者负责把规格与可执行行为对齐；教师决定课程验收结果。任何关于课程打分、组员贡献、真实模型收益的事实，只有对应责任人的记录或实际运行证据才能确认。

## 边界与约束

本次不改变 `configs/trina.yaml` 中的目标范围、动作等级或预算，不增加目标工具，也不重新解释既有测试断言。课件方法迁移到 Trina，课件示例系统的邀请、论文匿名化和评审账号不会被写成 Trina 功能。原课件只作为参考来源，仓库保留页码和摘要，不上传教师课件全文或课堂照片。

文档记录实际具备的能力和限制。当前覆盖统计尚不能严格区分“控制器允许”与“工具成功完成”，状态文件也不提供完整的进程级断点续跑。将这些问题写成已经完成，会使后续验收建立在错误假设上，因而必须进入未决问题和任务的退出限制。

## 意图变更与纠正

意图状态采用 `Draft → Clarify → Accepted / Rejected / Deferred`；替代旧意图时增加 `Superseded` 记录并保留原文。本段是文档治理规则，产品代码没有实现 Intent 审批服务。新请求若涉及真实模型付费试验、授权扩张、自动恢复执行或状态结构迁移，需建立新 Intent，说明影响、责任人和接受理由，再更新规格与任务。

维护者可以纠正需求和范围；教师可以指出课程清单映射错误；实测可以反驳文档中的实现主张。修订时保留稳定 `INT`、`REQ` 和任务 ID，通过 Git 提交记录说明变更原因。事实、假设、决策和问题的分类见 [问题框架](problem-frame.md) 与 [未决问题](open-questions.md)。
