## 已修正的证据判定缺陷

### 假设状态

旧实现把“本次新增发现且工具成功”作为确认条件。因此，即使发现只有 `detected` 状态，也可能把当前假设推进为 `confirmed`；相反，同一发现从 `detected` 升级到 `verified` 时，ID 没有变化，又可能漏掉确认。

任务模式与对话模式现在共用 `HypothesisLedger.record_tool_outcome()`。自动确认要求本次工具结果同时满足：

1. 漏洞类、目标位置与假设匹配；假设指定参数时，参数也必须匹配。
2. 发现为 `verified` 或 `exploited`，且本次发现带有证据。
3. 工具执行成功，且没有被拒绝。

文本假设仍可入账，但未绑定结构化验证对象时保持未解决。既有假设通过 `hypothesis_id` 复用。同一位置的发现升级后沿用原 ID 并更新关联证据。不同目标上相同文字的假设分别保存。

连续无新信息只降低优先级，保留未解决状态。只有明确传入反证及其证据时才允许进入 `refuted`；现有工具协议尚未自动生成这类反证。已确认记录不会因后续超时或重复输出丢失。

### 进展与停止条件

旧实现只要收到非空 `facts` 就计为新增进展，重复返回相同端口或发现也能重置停止计数。现在比较合并前后的事实指纹，排除时间字段、重复证据和运行计数；发现状态升级会计为进展。

这里的指纹衡量结构化事实变化，尚未覆盖所有原始输出的语义变化。原始输出中的动态文本也可能影响循环识别，仍需后续按工具类型补充归一化规则。

工具参数和结果指纹覆盖完整内容，避免只在长参数或长输出末尾出现差异时被误判为重复。结构化数据中的时间与耗时字段不参与结果指纹。

### 结果与工作台

模型 `final.status` 和 `final.flags` 不再直接改写运行结果。成功状态由工具事实与任务条件决定，确认漏洞要求同时具备验证状态和证据。明确要求确认漏洞时，带证据的疑似发现仍不能满足目标。

工作台周期保存最新假设及循环统计。证据图对未确认关联使用“关联线索”，只为确认假设显示“验证为”，并跳过不存在的发现引用。

这些改动提高了现有验证结果的可信度。系统仍信任已注册工具提供的证据与状态，独立 Proof Engine 尚未完成。

## 实施顺序与验收门槛

1. **独立 Proof Engine**：先覆盖 SQLi/LFI/RCE 三种已有验证工具。为每条结论保存固定请求、判定器版本、预期标记与环境标识，通过原执行链重放，产生独立验证记录。正例、软 404、错误页、缺证据与目标变化都要有回归样例。发现工具自带的 `verified` 字段不能直接替代独立验证结果。
2. **可恢复调度**：任务节点保存依赖、假设、动作、重试次数和检查点。恢复时重新加载当前授权与撤权信息，核对依赖和工件，再执行未完成节点。验收要求进程终止后续跑，保留已有证据，且不重复执行已完成检查。
3. **策略比较与晋级**：固定模型、场景版本、预算与环境，多次运行基线和候选策略。比较验证成功率、成功成本、首证据时间、重复率与恢复率；越界硬约束独立判定。已有 `E4` 实验明确缺少 A/B 对照，不能用其单次结果宣称性能提升。
4. **Studio 与 Binary 垂直能力**：工作台先消费稳定的 Core 状态和事件接口；二进制模块先做文件识别、静态函数关系与单个崩溃复现的端到端样例，再扩展调试器和架构。

近期验收重点是“同一结论可以独立重放、失败运行可以续跑、策略改进可以比较”。大规模多 Agent 并行、工具商店和自动改写 Prompt 暂不进入实施优先级。
