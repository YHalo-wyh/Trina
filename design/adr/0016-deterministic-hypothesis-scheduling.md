# ADR-0016：确定性假设调度——让台账优先级真正影响动作选择

- 状态：已采纳
- 相关：ADR-0003（单一收口）、ADR-0012（固定骨架 vs 动态选择）、ADR-0015（洞察层）、E4 / E6 实验卡

当前规则的逐步解释见[设计决策](../../设计决策.md)第 9 节。下文实验数字保留原实验背景；2026-10-26 补充的说明不构成新的真实模型效果试验。

## 背景
ADR-0015 把假设写进台账、按优先级排序、并塞进提示词。E4 实测暴露了它的边界：

* 洞察层让同任务 token **+44%**（9807 vs 6801），但**动作仍由模型自由选择**——
  优先级只是"建议"，模型可以一直不去验证最高优先级的那条；
* `docs/TARGET_PROGRESS.md` 把这条列为权重最高的缺口（"假设驱动决策与调度 15/8：优先级目前主要进入提示词，
  动作仍由模型选择；没有依赖图、确定性选取和任务重调度"）。

实测两个反例（都在本文件记录，均来自真机跑分）：
1. 模型把 `hypothesis.vuln_class` 写成阶段名 `recon` → 5 次"调度"全部无法验收，纯烧 prompt；
2. 任务要求验证 SQLi/LFI，台账里只有信息泄露假设 → 调度死盯 `dir_enum`，预算烧光还没拿到 flag（结论 NOT_CONFIRMED）。

## 决定
新增 `trina/brain/scheduler.py`（`HypothesisScheduler`），在**不破坏单一收口**的前提下补上确定性的一段：

1. **只调度能落地的项**：候选必须绑定到某个注册检查项（`RegisteredTest.expect_finding` ↔
   `hypothesis.vuln_class`，用与评分同一套 `normalize_vuln_class`）。绑定不到就不调度——
   "确定性"的定义是**有可执行的检查项**，不是"发一条无法验收的指令"。
2. **任务硬性要求优先**：`GoalRequirements.classes` 里的类只要有可绑定假设就独占候选；
   若模型还没为这些类提出假设，**目标驱动调度**直接在注册表里挑该类的检查项派下去
   （`source="goal"`，`hypothesis_id` 为空）。任务要求是硬约束（未满足不允许收敛），调度不得与之打架。
3. **限制部分重复绑定**：读取实时 `controller.executed`；某条假设已有尝试时，选择未记录执行的同类检查，都已记录则不再为该假设绑定。尚未尝试的新假设仍可能复用同类第一项，不能据此承诺全局只执行一次。目标驱动分支则在归组前排除已记录项。
4. **遵从性可审计**：双方有明确 `test_id` 时必须一致；实际 ID 未解析出时才回退工具名匹配。同工具的另一条明确检查不算遵从。
   未遵从记入 `state.counters["scheduler_miss"]`、`state.scheduler`，并**进审计哈希链**（`react.schedule`）。
   连续 `escalate_after`（默认 2）次未遵从 → 指令升级为硬提示，但**不阻断工具、不代模型编造证据**。
5. **可关**：`run.hypothesis_scheduler`（默认 `true`），与 ADR-0015 的两个开关同源；关闭后回到"只进提示词的排序建议"。
6. **度量**：`state.scheduler`（决策数、目标驱动数、遵从率）+ 评测指标 `hypothesis_resolution_rate`
   与 `scheduler_compliance_rate`（`docs/EVAL.md` §1.2）；工作台与报告新增"调度遵从"一行。

## 实测验证
- `tests/test_insight.py`（38 项）：绑定（含 `SQL Injection` 别名归一化）、阶段名不调度、低优先级跳过、
  试过的检查项不重复绑定、目标类优先于更高优先级的非目标假设、目标驱动调度、遵从计数与升级、
  开关关闭后无调度统计（集成用 ReplayBackend 断言提示词与计数器）。
- 真机（lab，`--goal "验证 SQL 注入与文件包含并拿到 flag"`）：调度指令进提示词，`react.schedule` 记录
  期望/实际/遵从，`scheduler_miss` 与遵从率落进 `state.json`；修正前那轮（死盯信息泄露）结论 NOT_CONFIRMED，
  修正后同类任务可拿到 CONFIRMED 与 flag。
- A/B（`review/experiments/E6-scheduler-ab.md`）：开关只差 `run.hypothesis_scheduler`，逐次数据入库。

## 后果
- 正面：台账优先级从"提示词建议"变成"可验收的指令 + 可复核的遵从率"；目标类验证不再靠模型自觉；
  未遵从不再是隐形的——它在哈希链里。
- 负面：提示词再长一段（每步一行调度指令）；调度可能替模型做了"先验哪个"的选择（用 `source` 与
  `state.scheduler` 记录，可复核、可争论）；模型硬不遵从时会多花提示词成本。
- 已知边界：调度质量取决于**注册表覆盖**（没注册的漏洞类无法调度）；`vuln_class` 写法不规范会静默失去调度
  （用"绑定不到就不调度"兜住，并在提示词里明确要求写发现类型）；本轮未测"调度是否提升最终成功率"。

## 被否决的方案
1. **直接派发绑定工具**：当前绑定主要依据漏洞类，位置、参数和前置条件尚不完整，直接执行会放大错配后果。若未来补齐绑定并仍走控制器、审批和注册表，这一方案可以满足单一执行入口；当前选择方向调度是具体工程取舍，不是对所有直接派发实现的否定。
2. **无绑定也调度**（发"请验证 sqli"这类自由指令）：实测烧 prompt 且遵从率无法测（5 次决策 0 次可验收）。
3. **把目标要求写进调度提示词就完事**：这只是把冲突交给模型裁决；实测模型会跟着目标走、忽略台账调度，
   遵从率 0.25——调度与目标必须同一口径。
