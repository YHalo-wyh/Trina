# ADR-0014：夹具自愈——谁拉起谁回收，评测器自己保证靶机在场

- 状态：已采纳
- 相关：ADR-0012、ADR-0013

## 背景
长跑评测与演示反复遇到同一类失败：**靶机被环境回收**（进程收到 SIGTERM），
表现为"某个场景莫名其妙全部失败"（工具连接被拒），而这与 Agent 能力无关。
一次实测：web 套件第二轮出现 3 个场景 0 步失败，原因是模型侧/夹具侧的瞬时故障被记成场景失败。

## 决定
1. **声明依赖**：场景可写 `fixtures: ["127.0.0.1:9099", "127.0.0.1:2222"]`（外加从 target 自动推导）；
2. **评测器自拉起**：`EvalHarness.start_lab_fixtures()` 在端口未监听时**进程内**启动 `trina.lab`
   （HTTP / SSH），跑完 `stop_lab_fixtures()` 回收；
3. **不碰别人的靶机**：已在运行的外部靶机只被复用，不会被重复拉起或关闭；
4. **`play` 同规则**：自动拉起的靶机会在任务结束时回收（`--keep-lab` 可保留）；
5. **失败要归因**：LLM 后端失败加重试与退避（`MAX_LLM_RETRIES`），单场景异常记为 `error` 而不是静默通过。

## 实测验证
- `tests/test_eval_report_lab.py::TestLabFixtures`：缺失夹具被自动拉起、跑完被回收；已存在的夹具不被碰；
- `trina play` 实测：冷环境下自动起 HTTP+SSH 两个靶机 → 跑完 → 回显"已回收本次自动拉起的靶机"；
- 控制台实测：同一流程在交互模式下同样自愈（长跑不再依赖手工起的靶机存活）。

## 后果
- 正面：评测/演示**一键可跑**；靶机被回收不再污染指标；回收责任明确（谁起谁收）。
- 负面：进程内夹具与评测共享进程，夹具崩溃可能影响评测进程（用异常隔离 + 端口探测缓解）。
- 已知边界：**不覆盖**外部真实靶场（Pikachu/DVWA/VulnStack 等仍需自行部署或远程可达）。

## 被否决的方案
"评测前人工起靶机 + 文档提醒"：长跑中靶机被回收仍会失败，且失败原因难以区分（Agent 差 vs 环境差）。
