# ADR-0011：评测口径——按声明范围评分、端口感知匹配、基础设施类不计误报

- 状态：已采纳
- 相关：ADR-0007、ADR-0009

## 背景
第一轮 Web 套件评测暴露了三个**口径问题**（不是模型问题），它们会把结论系统性带偏：
① 场景 GT 之外的**真实**发现（如顺带报出的缺失安全响应头）被算成误报；
② GT 匹配用 OR 语义（GT 只写 url 时，任意同类 finding 都命中），掩盖漏报；
③ 额外发现的真实端口/服务（覆盖更多）被算成误报。

## 实验数据（本仓库实测，两轮 web 套件）
| 项 | 修前 | 修后 |
|---|---:|---:|
| precision | 57.1% | **100%** |
| FPR | 42.9% | **0%** |
| FP / TP / FN | 6 / 8 / 1 | 0 / 8 / 1 |

> 两轮原始报告都在 `reports/eval/`（不入库，可本地复现）；结论与口径写进 `docs/EVAL.md §1.2`。

## 决定
1. **按场景声明范围评分**：范围默认取该场景 GT 的漏洞类集合（可显式覆盖）；
   范围外发现单列 `out_of_scope`，**不计入误报**；
2. **GT 匹配用 AND 语义**：类归一化相同后，GT 里声明了的 `url`/`parameter` 必须全部满足
   （比较前去掉 scheme，支持 `/sqli` 这类路径写法）；两者都未声明才算"同类即命中"；
3. **基础设施类发现**（`open_port` / `service_fingerprint`）超出 GT 不计误报——那是**额外覆盖**，
   由「端口覆盖率 / 服务识别准确率」两个指标衡量；
4. 主机类场景把扫描事实按 GT 口径转成发现后再匹配（否则覆盖度永远统计成遗漏）；
5. 场景可声明 `success_criteria`（auto/findings/findings_all/ports/flags），并支持 `fixtures` 声明依赖夹具。

## 后果
- 正面：precision/FPR 反映真实质量，可用于对比不同提示词/工具版本；复核者能解释每个 FP/FN 的来源。
- 负面：口径更复杂（需要维护 GT 的 `url`/`parameter` 字段）；场景写歪会误判（已在 `docs/EVAL.md` 写明如何检查）。
- 已知边界：范围默认由 GT 推导，若 GT 本身不全，范围外发现可能掩盖真实漏报——需人工审 GT。

## 被否决的方案
"所有未命中 GT 的都算误报"（简单但系统性惩罚正确行为）、"只看通过率不看 FP/FN"（无法区分漏报与误报）。
