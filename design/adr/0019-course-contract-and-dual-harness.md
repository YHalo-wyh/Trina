# ADR-0019：课程工程契约与双层 Harness

- 日期：2026-10-21
- 状态：本次文档交付采用；产品重大行为变化另行决策
- 基线：`24fb637`
- 关联：INT-02、REQ-19、REQ-20、TASK-08

## 背景

仓库已有架构、护栏、运行手册和 A1–A8 简表，但缺少独立的规格正文、GWT 场景、带依赖的任务卡以及需求到证据的追踪入口。章节 02 还区分 Runtime Harness 与 Project Harness，要求记录 Intent、权威来源、上下文可见性、Host 权责和连续性。仅增加一段 README 无法让复核者验证这些关系。

## 决策

沿用现有产品架构，在 `docs/course/` 组织课程工程契约，首页提供短入口，技术细节继续引用原有架构资料。规格正文负责行为规范，追踪清单只负责 ID 关系和验证定位，避免把 JSON 再变成第二份自然语言需求。文档检查核对关系和本地链接，实际功能证据仍来自已有自动化测试与固定决策回环运行。

Runtime Harness 描述模型路由、执行链、预算、状态及重试；Project Harness 描述规格、资料、规则、测试、审查和恢复。Host 指现有 Python 宿主及操作者管理的配置、工具和批准，不引入新的身份服务，也不把课程的人类批准伪造成产品 API。

## 比较过的方案

| 方案 | 收益 | 代价与不采用原因 |
|---|---|---|
| 所有内容写入 README | 单入口，容易开始阅读 | 正文过长，代码使用说明与规格混杂，单条要求难追踪，未采用 |
| 按课件示例重新构建论文平台 | 与示例名称一致 | 偏离已有 Trina 和用户提交对象，重复实现且扩大范围，未采用 |
| 引入外部需求平台和复杂 CI | 可提供数据库及审批流程 | 新增账号、服务和维护成本；课堂检查依赖外部环境，未采用 |
| 同仓库 Markdown、JSON 关系及本地验证 | Git 版本一致，能直接检查和复现，额外依赖少 | 文本充分性仍需人工判断，采用 |

## 后果与限制

教师可以从 REQ 追到场景、任务、测试与原始事实，后续改动必须同步这些关系。增加文档不会自动修复覆盖、权限绑定、脱敏或取消语义；这些缺口保留在问题清单，不用文档声明替代代码工作。同行审查和签署也不由脚本生成。

检查脚本通过意味着结构和引用有效，不意味着完整业务验收。维护者需要避免为了通过脚本而填入不相干测试，因此人工抽查至少三条跨层要求仍为验收流程的一部分。

## 回滚与重决策条件

文档及脚本通过正常反向提交可回滚到 `24fb637`，不改变产品数据。若未来需求数量显著增长、跨仓库复用或多人审批出现实际需求，再比较生成式文档与外部管理平台。若 trace 检查长期只验证字面 ID 而不能发现真实漂移，应补充契约验证或缩减无效字段，保留已有 ID 的历史。
