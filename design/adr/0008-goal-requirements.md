# ADR-0008：把任务描述解析为硬条件（目标要求机制）

- 状态：已采纳（M4 后修复）

## 背景
评测中实测到一个真实缺陷：对 `web-sqli` 场景（要求"确认 /sqli 的 SQL 注入"），
Agent 发现靶机直接暴露 `/flag`，拿到 flag 后就收敛，**从未验证 SQL 注入**，状态还报 success。
这不是指标口径问题，而是 Agent 用"顺手拿到的战果"替换了"任务要求的验证"。

## 决定
从任务描述（`--goal` / 场景 goal）解析出硬条件，未满足前不允许收敛，也不允许把取巧结果判为成功：

| 解析对象 | 例子 | 语义 |
|---|---|---|
| 漏洞类 | "SQL 注入"、"文件上传"、"弱口令" | 需有**带证据**的对应发现（有类要求时路径要求降级为提示） |
| 路径 | "/.git/HEAD"、"读取 /admin/config.php" | 无类要求时作为硬条件 |
| 端口 | "必须覆盖 9099 与 2222" | 未出现在扫描结果里就不收敛（年份/时长/任务编号不算端口） |
| 明文凭据 | "用户名 trina、口令 trina123"、"admin/admin123" | 生成"用单次验证而非爆破"的提示 |

实现：`trina/brain/goal.py#GoalRequirements`；终止判定读取它；模型提前给出 `final` 时最多拒绝 2 次
（之后尊重其判断，避免死循环）。

## 后果
- 正面：`web-sqli` 等场景从"FN + 假 success"变成真实验证；弱口令场景从 0/1 变成 1/1；
  离线回放测试可断言"只有 flag 不得判成功"。
- 负面：目标写得含糊时（如只说"测试一下"）不产生硬条件——这是刻意的，避免凭空发明约束。
- 已验证：`tests/test_brain.py::TestGoalRequirements`、`test_flag_shortcut_does_not_satisfy_task_goal`。

## 被否决的方案
把 ground truth 喂给 Agent：直接泄题，评测失去意义（本机制只用任务描述，不用真值）。
