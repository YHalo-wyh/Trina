# ADR-0001：宿主掌握决策循环，模型后端保持可替换

- 状态：已采纳；2026-10-26 补充设计依据，未改变产品执行逻辑。
- 适用范围：`PentestAgent`、`ChatAgent` 与 `trina.llm` 的职责划分。
- 关联：[动作协议](0002-text-json-action-protocol.md)、[执行入口](0003-single-execution-chokepoint.md)、[配置授权](0004-policy-from-config-not-prompt.md)、[确定性调度](0016-deterministic-hypothesis-scheduling.md)。
- 逐步设计说明：[设计决策](../../设计决策.md)。

## 1. 决策背景

Trina 需要根据目标状态决定下一步。固定扫描列表可以覆盖已知流程，但不能充分处理新的路径、凭据、错误和验证线索；模型可以根据观察调整动作，却可能忽略范围、重复尝试或提前宣布成功。系统因此同时需要可变的候选决策和稳定的执行控制。

仓库已有 Python 工具、范围校验、审计和结构化状态。引入模型后，必须明确谁决定执行、谁更新事实、谁消耗预算，以及模型结束声明能否直接影响成功状态。这些问题如果隐藏在某个后端内部，课程检查和回归测试就难以定位具体判断点。

该决策解决的是控制归属。模型接入可以复用已有能力；目标权限、状态写入、执行生命周期和验收语义由项目宿主掌握。这里的宿主指维护者控制的 Python 程序与配置，不是额外部署的 Web 管理平台。

## 2. 选择方案前需要满足的条件

| 条件 | 具体要求 | 对循环设计的影响 |
|---|---|---|
| 每步可裁决 | 候选动作进入工具前可检查目标、注册项、预算及人工决定 | 需要显式的动作接收和执行控制点 |
| 结果可归因 | 能找到哪次调用产生哪条发现、错误和证据 | 动作、观察和状态更新必须保留关联 |
| 模型不可自证 | final.status 和模型自报 flag 不能直接成为验证事实 | 收尾必须读取工具事实与目标条件 |
| 故障可处理 | 格式错误、网络错误、工具异常和预算耗尽有不同反馈 | 循环需要访问结构化错误，不能只收到最终一段文本 |
| 验证可重放 | 固定模型输出后可重复检查执行机制 | 后端接口需支持记录与 ReplayBackend |
| 后端可替换 | 更换模型接入方式时不重写全部工具和状态 | 后端只返回响应与用量，业务循环位于稳定接口之外 |

这些条件可以由自有循环实现，也可以由具备足够控制接口的通用框架实现。评估重点在于接口是否覆盖当前要求，以及集成、迁移和长期维护成本。

## 3. 备选方案与选择理由

### 3.1 固定脚本串接工具

固定脚本的调用次序清楚，容易重跑，也适合当作回归夹具。它的不足在于不能很好地处理“发现了原计划之外的路径”“需要换参数验证”或“当前服务不可达”的情况。若为每种观察不断增加分支，计划维护会逐渐变成庞大的手工规则树。

因此，固定脚本保留在回放及机制验证中，用来隔离和测试执行链；面向多样任务的主控仍允许模型提出动作。

### 3.2 将整项任务交给外部 Agent 循环

外部循环可以提供上下文、工具路由和重试能力，减少重复开发。但项目需要逐项确认它是否提供执行前裁决、真实参数检查、撤权、共享预算、取消、状态写入和可重放的调用接口。若只能收到最终回答，便无法落实本项目的逐动作证据要求。

该方案没有被证明在所有框架中都不可行。当前没有为了复用外部循环而迁移已有工具契约，是因为迁移需要重新验证这些接口，收益不足以覆盖当下的集成与验收成本。未来框架能提供稳定接口时仍可重新评估。

### 3.3 宿主自有循环与可替换模型后端

主控将状态和任务转为提示，模型返回候选动作；宿主解析候选，调用控制器、审批和工具注册表，再将结果并入状态并继续。每个判断都有可定位的函数，现有 Python 模块无需改为另一套工具定义。

该方案与现有工程契约一致，也便于用假的工具和固定响应构造阴性用例。因此选为当前主方案。代价是提示词、解析容错、上下文预算、错误处理和状态维护需要自行负责，不能把“可控制”误写为“所有逻辑天然正确”。

### 3.4 默认多个 Agent 并发执行

并发角色可以分担探索，但需要处理共享预算、同目标并发、重复动作、状态写冲突和相互不一致的结论。当前执行生命周期和位置绑定仍有缺口，直接增加并发执行者会扩大协调复杂度。

现有方案采用可选的建议型咨询：子角色只接收快照并返回建议，执行仍回到主控的普通工具动作。这一选择保留专业分析入口，同时减少多个写入者；真实收益需通过同条件实验验证。

## 4. 采纳的具体职责边界

`trina.llm` 负责模型调用和响应/用量，支持不同接入与固定回放。后端不会因返回一个 action 对象就自行执行项目工具；使用 omp 接入时，适配器按实现关闭其工具执行能力，保留模型接入用途。实际后端参数由配置和对应适配器负责。

`PentestAgent` 负责一次任务的循环，组合目标要求、阶段机、台账、方向调度、有限重试及确定性收尾。`ChatAgent` 负责对话请求及有限动作循环，复用执行和事实规则，但没有同等的阶段机、确定性方向调度和任务收尾协议。两类入口需要分别验收，不能把“共用组件”写成“全部语义一致”。

`AuthorizationController` 处理注册、撤权和预算；可选审批回调处理操作者决定；`ToolRegistry` 处理参数、可用性、等级、护栏、超时及结构化结果；`RunState` 保存工具事实；假设台账按匹配证据更新问题状态。模型提出的理由与建议保留为可复核声明，不具有修改授权或直接确认事实的权限。

## 5. 为什么选择逐步观察，而不预先执行整段计划

每执行一步，目标状态、剩余预算和可用证据都可能变化。单步观察使后续动作能够使用新信息，也给操作者留下介入位置。如果一次提交十个动作直接依次执行，第一个动作已经失败或权限已撤销时，后续九个动作仍可能基于过期条件。

逐步循环的代价是更多模型往返和更高延迟。对于参数固定、前置条件清楚的批量探测，可以在单个工具契约内部受控执行；对跨能力、依赖动态事实的计划，仍保留主控逐步决定。批量能力必须自行遵守范围、规模及超时规则，不能因包装成一个工具就免除执行约束。

## 6. 已知后果和保留限制

采用自有循环后，模型动作、工具结果、假设更新和收尾都有清晰测试入口，回放也能验证后端选择以外的机制。维护者同时需要承担多个入口保持一致的责任：相同证据规则可以共用，任务时长、对话自然语言返回和阶段推进等差异则必须明确记录。

当前控制器在允许时就更新 executed；线程超时不能强制取消在途行为；目标解析是关键词规则；调度以漏洞类型绑定为主；原始状态和观察没有统一敏感内容处理。这些限制不会因为循环由宿主维护就消失。详细含义及影响见决策层说明第 26 节和课程 OQ 清单。

状态快照支持读取和展示，尚不能恢复全部控制器、模型和在途工作。审计链提供内部一致性检查，尚不构成独立可信时间证明。自有循环为修复这些问题提供明确位置，但修复本身仍需代码和验证。

## 7. 如何判断这项决策是否满足要求

现有 `tests/test_brain.py` 检查范围预检、目标条件、协议容错、有限推进及回放；`tests/test_decision_evidence.py` 检查伪造 final、证据对象、重复事实及确认保留；`tests/test_collaboration.py` 检查建议无执行权、采纳后另发动作、对话事实连续性和原子快照。

机制运行使用固定响应配合真实 lab 请求，证明候选动作可以通过受控执行链形成证据、假设和报告。它不能证明模型自主探索水平优于其他架构。模型或调度效果比较应固定任务、模型、预算和评分口径，保存逐次结果与失败样本。

本次说明对应的实际验证记录见 [2026-10-26 文档验证](../../evidence/20261026-decision-docs/README.md)，历史机制证据见 [2026-10-21 课程验证](../../evidence/20261021-course-pack/README.md)。

## 8. 重新决策与迁移条件

当通用框架能稳定覆盖逐动作裁决、取消、状态事务、审计和重放，且适配成本低于继续维护自有循环时，可重新比较方案。迁移前应固定现有动作协议、工具契约与阴性用例，以相同轨迹核对新旧行为。

迁移必须保留现有产物读取和接口兼容，先在代表性任务中验证，再改变默认入口。旧轨迹和审计保持原样；出现边界、目标或事实回归时回到原入口，并按明确变更提交回滚。该决策记录负责说明控制归属，不授予未来迁移自动上线或扩大任务范围的权限。
