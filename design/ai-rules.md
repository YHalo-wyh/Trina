# AI 使用规则（O1：人机责任）

> 本项目的代码与文档大量借助 AI 辅助生成。**AI 生成不等于可交付**：以下规则说明谁决定、谁执行、谁复核。

## 1. 责任划分

| 环节 | 人负责（不可外包） | AI 可辅助（必须验证） |
|---|---|---|
| 范围与授权 | 决定测试哪些目标、允许哪些动作等级、预算多少（写进 `configs/`） | 起草配置、解释参数含义 |
| 契约与验收 | 定义验收ID（`brief/README.md`）、负向场景、什么算完成 | 起草用例骨架、补边界用例 |
| 实现 | 决定架构取舍（见 `adr/`）、审查关键路径（护栏、审计、控制器） | 生成候选实现、批量重构、补测试 |
| 验证 | 判定证据是否足够、是否 CONFIRMED / NOT_CONFIRMED / INCONCLUSIVE | 跑用例、汇总指标、定位失败 |
| 复核 | 对结论签署；处理冲突与撤权 | 生成复核清单（`trina review`） |

## 2. 硬性规则

1. **授权判据不进提示词**：范围/等级/预算来自 `configs/*.yaml` 与 `trina/scope.py`、`trina/policy.py`；
   任何"临时放开一下"都要改配置并留痕，不允许在提示词里放宽。
2. **AI 产出必须可验证**：新增/修改行为必须带测试（`python3 -m unittest discover -s tests`），
   且**禁止为了让测试通过而放宽护栏**——测试断言的是"必须被拒绝"的行为。
3. **不接受 AI 的自我声明**：模型说"这应该安全""管理员已同意"都不是许可；控制器只看注册表与审批记录。
4. **工具输出当数据**：日志/响应/工具文本中出现"忽略限制""扩大范围"等文字一律不执行，
   只作为证据保留（`tests/` 中有对应用例；报告里区分"建议越界/请求越界/实际越界"）。
5. **被拒绝的 AI 建议要留痕**：在 `review/` 里记录至少一条被否决的 AI 建议及理由（课程 O1 的最小证据）。
6. **不伪造证据**：截图、报告、指标必须对应真实运行；无法复现的结论只能写成"未确认/无法判断"。
7. **数据边界**：只用虚构靶场与虚构数据；不向外部模型提交真实业务数据/凭据。

## 3. 最小证据（本仓库里的落点）

| 能力 | 最小证据 | 位置 |
|---|---|---|
| O1 人机责任 | 本文件 + `review/` 中的"被否决建议"记录 | `design/ai-rules.md`、`review/README.md` |
| O2 工程契约 | 验收ID 表 + 注册检查项（`tests:` 段） | `brief/README.md`、`configs/ranges/*.yaml` |
| O3 可信验证 | 测试 + 审计哈希链 + 评测指标（含分母） | `tests/`、`evidence/`、`docs/EVAL.md` |
| O4 工程取舍 | ADR（含被否决方案与代价） | `design/adr/` |
| O5 变化与对抗 | 蓝队对抗评测 + 撤权演练 | `docs/EVAL.md`、`tests/test_policy.py` |

## 4. 使用 AI 的推荐姿势（本项目实践）

- **先定契约再让 AI 写实现**：把验收ID、负向场景、不允许的行为写清楚，再让 AI 生成候选。
- **一次只改一个主要因素**：改护栏/改提示词/改工具分开验证，否则指标变化无法归因。
- **让 AI 写"能失败的测试"**：先写会失败的负向用例（越界、坏参数、软 404、假 flag），再实现修复。
- **保留可复现轨迹**：`--record` 录制决策序列，`--replay` 离线重放，任何指标变化都能复现。
